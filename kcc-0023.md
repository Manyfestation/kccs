```
KCC: 23
Title: MJ: Metadata JSON
Description: Declares JSON metadata bound to a covenant ID, with meaning left to ecosystem conventions.
Authors: Sivan Helfer <sivan@manyfest.dev>
Status: Draft
Type: Standards Track
Category: Application
Requires: KIP-20
```

## 1. Abstract

KCC-23 defines a way to bind JSON metadata to a covenant ID. Deployment adds a
version 1 preparation transaction that carries the JSON in its payload and
creates an output. The genesis transaction then spends that output to initialize
the covenant. The covenant ID commits to the spent outpoint, whose transaction
ID commits to the metadata. The transactions can be shared as a launch proof,
allowing readers to verify the binding independently.

## 2. Motivation

Covenant applications may wish to publish descriptive information that their
spending rules do not enforce. A [KCC-20](kcc-0020.md) token deployer may want to
declare a name, symbol, or number of decimal places. These properties describe
the token as a whole and should not have to be repeated in every token UTXO or
carried through every transfer.

KCC-23 uses KIP-20's covenant ID hashing mechanism to bind the declaration to
the application's identity at genesis. Readers can then verify which metadata
was declared for a given covenant ID, regardless of who supplies it.

## 3. Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD",
"SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this
document are to be interpreted as described in RFC 2119 and RFC 8174.

### 3.1 Declaration

The metadata declaration (MJ) MUST be a JSON object encoded as UTF-8 and MUST
occupy the entire payload of the preparation transaction. There is no prefix,
wrapper, or required property. Field names and their meanings are left to
ecosystem conventions.

If an API represents payload bytes as a hexadecimal string, that string encodes
the UTF-8 bytes; the hexadecimal text itself is not stored in the payload.

The commitment covers the exact payload bytes, including whitespace and
property ordering. The declaration is fixed for that covenant ID.

### 3.2 Deployment

Deployment MUST use the following two transactions:

1. A version 1 preparation transaction carrying the metadata in its payload
   and creating an output to be spent at genesis.
2. A genesis transaction spending that output to authorize the application's
   genesis output group under KIP-20.

The preparation transaction's ID commits to the payload. Under
[KIP-20's genesis hashing rule](https://github.com/kaspanet/kips/blob/e4ae2332117b5cb68bd6188e065ef885b6d17939/kip-0020.md#3-covenant-id-genesis-hashing),
the covenant ID commits to the spent outpoint and the genesis output group.
Together, these commitments bind the metadata to the covenant.

### 3.3 Verification

Both transactions MAY be shared off chain as a launch proof, identifying the
output spent at genesis and the genesis output group. Verification is OPTIONAL
and does not depend on who supplies the proof. To verify the binding to an
expected covenant ID, a reader MUST:

1. Confirm that the preparation transaction is a version 1 transaction and
   its payload satisfies Section 3.1.
2. Recompute its ID from the original transaction fields and payload bytes
   using Kaspa's version 1 transaction-ID calculation.
3. Check that the genesis group's authorizing input spends an existing output
   of that preparation transaction, using the recomputed ID and output index.
4. Recompute the covenant ID from that outpoint and the complete genesis
   output group under KIP-20, and require it to match the expected covenant ID
   and the group's declared covenant ID.

The on-chain payload can also serve as a publication hint. When observing a
covenant genesis, a reader could follow its authorizing outpoint to the
preparation transaction and inspect its JSON payload for a description of the
application. Ecosystem conventions determine how to recognize and interpret
that description.

## 4. Example: token metadata

A [KCC-20](kcc-0020.md) token deployer places the following JSON in
the payload of a version 1 preparation transaction creating an output:

```json
{
  "name": "Example Token",
  "symbol": "EXT",
  "decimals": 8
}
```

The deployer then spends that output to authorize the initial token outputs in
the genesis transaction. The deployer can share both transactions as the launch
proof.

An application following these field conventions could label the token
"Example Token" and display a raw amount of `100000000` as `1 EXT`. Token
transfers require no metadata input or output. The field names and display
behavior are illustrative.

## 5. Rationale

The preparation transaction binds metadata through KIP-20's existing genesis
commitment without persistent metadata UTXOs or additional covenant state.
Requiring version 1 gives readers one transaction-ID calculation to support.
UTF-8 JSON provides a common format without a codec registry or application
schema.

## 6. Conformance Vectors

The authoritative machine-readable vectors are in
[`kcc-0023/vectors/conformance.json`](kcc-0023/vectors/conformance.json).
Byte strings are lowercase hexadecimal. These are synthetic commitment
fixtures, with placeholder outpoints and scripts.

The binding vector uses the example metadata serialized exactly as follows,
without a trailing newline:

```json
{"name":"Example Token","symbol":"EXT","decimals":8}
```

The preparation transaction has one input spending index 0 of transaction ID
`11` repeated 32 times, and one output of 100000000 sompi. The genesis
transaction spends preparation output 0 through input 0 and creates one
output of 90000000 sompi, bound to the resulting covenant ID. Both transactions
are version 1, use the native subnetwork, and have zero lock time, gas, input
sequence, compute budget, and storage mass. Signature scripts are empty; both
output scripts are version 0 with bytes `51`. The genesis payload is empty.

```text
preparation transaction ID = 43ba49710a8e6e3b19ce0c32cd9fa9e8644a290f16220249b460b846f92f1cc2
covenant ID                = 14390193cdd30d773852f697307c47953bd60c47264e26b0b008b93d23505b7a
```

Keeping the genesis transaction and expected covenant ID unchanged while
replacing `"decimals":8` with `"decimals":9` in the preparation payload MUST
fail binding verification. A version 0 preparation transaction MUST also fail.

The declaration vectors cover:

| Payload bytes | Interpretation | Valid declaration |
| --- | --- | --- |
| `7b7d` | `{}` | Yes |
| `7b226e616d65223a22c3a9227d` | `{"name":"é"}` | Yes |
| `5b5d` | `[]` | No, not an object |
| `7b2278223a22ff227d` | Invalid UTF-8 | No |

## 7. Security Considerations

KCC-23 binds descriptive metadata to a covenant ID. It adds no spending
authority and does not change the covenant's validation rules. Applications
determine how to interpret and use the metadata.
