```
Title: MJ — Metadata JSON
Description: Declares JSON metadata bound to a covenant ID, with meaning left to ecosystem conventions.
Authors: Sivan Helfer <sivan@manyfest.dev>
Status: Draft
Type: Standards Track
Category: Application
Requires: KIP-20
```

## 1. Abstract

KCC-23 defines a way to bind JSON metadata to a covenant ID. Deployment adds a
preparation transaction that carries the JSON in its payload and creates an
ordinary Schnorr UTXO. The genesis transaction then spends that UTXO to
initialize the covenant. The covenant ID commits to the spent outpoint, whose
transaction ID commits to the metadata. The transactions can be shared as a
launch proof, allowing readers to verify the binding independently.

## 2. Motivation

Covenant applications may wish to publish descriptive information that their
spending rules do not enforce. A [KCC-20](kcc-0020.md) token deployer may want to
declare a name, symbol, or number of decimal places. These properties describe
the token as a whole and should not have to be repeated in every token UTXO or
carried through every transfer.

KCC-23 uses KIP-20's covenant ID hashing mechanism to bind this declaration to
the application's genesis and identity. It requires no persistent metadata
UTXO, dedicated contract, or additional covenant state: the preparation output
is consumed at genesis, while the metadata remains committed by the covenant ID.

## 3. Specification

### 3.1 Declaration

**MJ** is a UTF-8 JSON object occupying the entire payload of the preparation
transaction. There is no prefix, wrapper, or required property. Field names and
their meanings are left to ecosystem conventions.

The commitment covers the exact payload bytes, including whitespace and
property ordering. The declaration is fixed for that covenant ID.

### 3.2 Deployment

Deployment uses two ordinary transactions:

1. Spend an ordinary Schnorr UTXO in a preparation transaction carrying MJ in
   its payload. Create a Schnorr output without a covenant binding.
2. Spend that output in the genesis transaction to authorize the application's
   genesis output group.

The preparation transaction's ID commits to the payload. Under
[KIP-20's genesis hashing rule](https://github.com/kaspanet/kips/blob/e4ae2332117b5cb68bd6188e065ef885b6d17939/kip-0020.md#3-covenant-id-genesis-hashing),
the covenant ID commits to the spent outpoint and the genesis output group.
Together, these commitments bind MJ to the covenant.

### 3.3 Verification

The metadata and both transactions can be shared off chain as a launch proof,
identifying the output spent at genesis and the genesis output group. Readers
could verify the binding by recomputing the preparation transaction's ID from
its original contents, including the payload, checking the spent outpoint, and
recomputing the covenant ID under KIP-20. This uses Kaspa's transaction-ID
calculation for the transaction's version. Verification is optional and does
not depend on who supplies the proof.

The on-chain payload can also serve as a publication hint. When observing a
covenant genesis, a reader could follow its authorizing outpoint to the
preparation transaction and inspect its JSON payload for a description of the
application. Ecosystem conventions determine how to recognize and interpret
that description.

## 4. Example: token metadata

A [KCC-20](kcc-0020.md) token deployer places the following JSON in
the payload of a transaction creating a Schnorr output:

```json
{
  "name": "Example Token",
  "symbol": "EXT",
  "decimals": 8
}
```

The deployer then spends that output to authorize the initial token outputs in
the genesis transaction. The deployer can share both transactions as the launch
proof.

An application following these field conventions could label the token
"Example Token" and display a raw amount of `100000000` as `1 EXT`. Token
transfers require no metadata input or output. The field names and display
behavior are illustrative.

## 5. Security Considerations

KCC-23 declares descriptive metadata; it adds no on-chain application logic or
spending authority. The binding makes the declaration verifiable, but does not
guarantee that its contents are true.
