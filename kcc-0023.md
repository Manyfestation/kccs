## 1. Abstract

KCC-23 provides a mechanism for covenant applications to declare descriptive
information independently of their spending rules. A dedicated metadata instance
holds a JSON object as its only state field. The genesis declaration is permanently
committed to the application's covenant ID, as described in
[Section 3.2](#32-genesis-binding). Readers can verify that the metadata belongs
to that covenant; ecosystem conventions determine how its fields are interpreted
and used.

## 2. Motivation

Covenant applications may wish to publish descriptive information that their
spending rules do not enforce. For example, a [KCC-20](kcc-0020.md) token deployer
may want to declare a symbol or the number of decimal places used to display an
amount. These properties describe the token as a whole and should not have to be
repeated in every token UTXO or carried through every transfer.

An external service can supply this information. Readers may wish to verify that
it was declared when the covenant was created, regardless of where they obtain
it. KCC-23 offers this connection through a declaration bound to the covenant ID,
keeping metadata separate from application
operations while making its origin verifiable. The choice of fields and their
meaning remain matters of ecosystem convention and social consensus.

## 3. Specification

### 3.1 Metadata instance

A **metadata instance** is a [KCC-1 covenant instance](kcc-0001.md#4-core-concepts),
a UTXO locked to a metadata program. It has exactly one state field, exposed by
the Program ABI as the `MJState` record:

```text
MJState {
    json: byte[N]
}
```

`json` holds a UTF-8 JSON object, and `N` is its byte length. The program follows
KCC-1's [state encoding](kcc-0001.md#81-state-encoding) and
[P2SH envelope](kcc-0001.md#7-p2sh-covenant-envelope), with `N` fixed for its
state layout. Property names should be unique to avoid ambiguous interpretation.
The Program ABI should describe the state layout, template, and entrypoints so
readers can decode the state and construct invocations. `MJState` is the ABI
record name; it does not add a marker or property to the JSON object.

The metadata instance serves only to declare metadata. Application transitions
MUST NOT depend on consuming or reproducing it. Its permitted continuations are
defined in [Section 3.4](#34-spending-and-continuations).

### 3.2 Genesis binding

A covenant adopting KCC-23 MUST include exactly one metadata instance in its
genesis output group, sharing the group's covenant ID and authorizing input.

[KIP-20's genesis hashing rule](https://github.com/kaspanet/kips/blob/e4ae2332117b5cb68bd6188e065ef885b6d17939/kip-0020.md#3-covenant-id-genesis-hashing)
derives the covenant ID from the authorizing input's outpoint and the genesis
group's outputs, including their script public keys. The metadata instance's P2SH
script commits to its full program, including the JSON state, so including that
instance in the genesis group also binds the exact metadata bytes to the
covenant ID.

The commitment covers the exact stored bytes, including whitespace and property
ordering.

### 3.3 Publication and verification

The metadata program, including its JSON state, can be shared off chain before
the instance is spent. Readers can verify this preimage against the genesis
output's commitment, regardless of who supplied it.

Spending the instance reveals its program and JSON on chain, even if it
terminates. The program can also be published on chain separately. Once
available on chain, it can be retrieved directly from chain data. KCC-23 does
not prescribe a publication format or distribution service.

To verify a declaration, readers MUST:

1. Check that the supplied program matches the genesis output's P2SH commitment.
2. Verify the genesis group against the covenant ID using KIP-20's hashing rule.
3. Decode the JSON state using the `MJState` layout.

These checks establish that the metadata was committed at the covenant's
creation, whether the program was obtained on or off chain.

### 3.4 Spending and continuations

The metadata instance can remain unspendable, terminate, or produce metadata
continuations. Every continuation it authorizes MUST preserve its authenticated
[KCC-1 program template](kcc-0001.md#85-continuation-programs) and `MJState`
layout. The metadata program MUST NOT permit a transition to an application
program with a different template.

This restriction applies to every output in the metadata input's
[KIP-20 authorized-output context](https://github.com/kaspanet/kips/blob/e4ae2332117b5cb68bd6188e065ef885b6d17939/kip-0020.md#52-authorized-outputs-context-per-input),
including when other inputs in the transaction carry the same covenant ID.
The program MUST enforce it on every spending path. Termination leaves no
authorized continuations; KAS can be returned through outputs without a covenant
binding.

Spending the instance does not remove the commitment to the genesis declaration.
A continuation may carry different JSON bytes if the program permits, but it
does not replace that declaration. Conventions for interpreting later metadata
as an update are outside the scope of KCC-23.

An owner-controlled instance MAY keep its owner's public key in the program
template, outside state, and require an owner signature following
[KCC-2](kcc-0002.md). The owner can then authorize a spend that reveals the
metadata and returns the instance's KAS. JSON remains the only state field.
Owner control is optional and remains subject to the continuation restrictions
above.

In Argent terminology, this corresponds to a metadata actor whose `become`
routes return only to itself, or which terminates. This is an illustrative
mapping; the requirements above apply to covenant programs regardless of
compiler.

## 4. Example: token metadata

A [KCC-20](kcc-0020.md) token deployer could include a metadata instance alongside
the initial token outputs in the same genesis group. Its JSON state might be:

```json
{
  "name": "Example Token",
  "symbol": "EXT",
  "decimals": 8
}
```

After verifying the declaration, an application following these field
conventions could label the token "Example Token" and display a raw amount of
`100000000` as `1 EXT`. Token transfers can proceed without reading or spending
the metadata instance. The field names and display behavior here are illustrative;
KCC-23 leaves their definition to the conventions adopted by each application.

## 5. Security Considerations

A verified declaration is not a guarantee that its contents are correct.
Readers MUST treat metadata as untrusted input.

The commitment proves the genesis declaration's connection to a covenant. It
does not establish the deployer's real-world identity or ownership of a name or
symbol.
It also does not guarantee that an unrevealed program will remain available;
metadata shared only off chain depends on someone retaining and supplying it.

A metadata instance carries the application's covenant ID. Without the
continuation restrictions in Section 3.4, spending it could create instances of
other application programs under that same ID, bypassing their intended
creation rules. Preserving the metadata template keeps its continuations
confined to the metadata program.

Even with this restriction, a spendable metadata instance can participate in a
transaction under the application's covenant ID. Applications MUST NOT accept
its participation alone as business authorization; they must
check the relevant application programs and rules as well.
